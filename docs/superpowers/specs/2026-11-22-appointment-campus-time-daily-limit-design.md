# 预约网点、时间与每日提交限制设计

日期：2026-11-22

## 目标

预约必须关联微信用户、自习室网点和明确的未来到店时间。每个微信用户按北京时间自然日最多提交 10 条预约。运营后台能够查看预约网点与时间，并按网点筛选预约线索。

## 数据结构

沿用 `leads` 作为预约表。`campus_id` 已存在并关联 `campuses.id`，本次改为非空，不新增 JSON 扩展字段。新增非空的 `appointment_at` 时区时间字段，保存完整预约日期和时间。为每日限额和后台筛选增加 `user_id + created_at`、`campus_id + appointment_at` 索引。

由于产品尚未正式上线且测试数据可清空，部署时重建业务表，不编写旧数据回填逻辑。

## 小程序

预约页加载公开网点列表。网点、日期和时间均为必选项；日期不能早于今天，组合后的预约时间必须晚于当前北京时间。日期使用微信原生日期选择器，时间使用 24 小时制原生时间选择器，精度为分钟。

从网点或兴趣活动详情进入预约页时，已有 `campus_id`、`campus_name` 和 `course_id` 继续作为预选值。直接进入预约页时，用户必须手动选择网点。

预约历史显示网点、预约时间、孩子年龄与年级、跟进状态和备注。服务端的字段错误、每日限额错误直接作为 Toast 提示。

## 服务端验证与限额

`POST /api/public/leads` 必须携带有效家长微信会话。服务端验证：网点存在且为 `published`、预约时间格式有效且在未来、年龄和年级有效。

每日限额直接基于数据库预约记录计算，不使用进程内存或文件。内存会在容器重启时清零，多进程也无法共享；数据库记录能够持续、审计并适配未来扩容。

每次提交先锁定当前 `users` 行，再统计该用户在北京时间当天对应 UTC 时间区间内的 `leads` 数量。前 10 条允许创建，第 11 条返回 HTTP 429，提示“每天最多提交10条预约，请明天再试”。用户行锁保证同一微信用户的并发请求串行计数，避免同时提交突破限制。

## Admin 后台

预约线索列表增加网点筛选器，选项来自全部网点；查询参数为 `campus_id`。列表显示“网点名称”和格式化后的预约时间。首页待跟进预约同步显示网点和预约时间。
