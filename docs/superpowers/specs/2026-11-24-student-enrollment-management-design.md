# 学生报名管理设计

## 背景

当前后台将第一条报名记录嵌在学生编辑页中，容易让运营人员误以为一个学生只能有一条报名。实际业务需要支持同一学生多次报名和续费，并保留完整的报名与到店历史。

## 产品规则

- 后台“学生管理”改名为“学生报名管理”。
- 主列表每个学生只展示一行，不因续费产生重复学生行。
- 学生详情页展示学生档案和该学生的全部报名记录。
- 新增续费通过详情页的“新增报名记录”进入独立表单，不重复创建学生档案。
- 报名记录按开始日期倒序展示。
- 同一学生的全部报名记录使用统一日期范围校验，不区分网点或服务项目。
- 日期区间按闭区间计算：`开始日期 <= 日期 <= 结束日期`。两个记录只要共享一天就视为交集，不能保存。
- 编辑报名记录时排除当前记录自身后再检查交集。
- 报名记录的展示状态按日期计算为：已结束、当前生效、待生效。数据库中的记录状态继续保留，用于停用等人工操作。

## 后台交互

### 学生报名管理列表

- 路由和导航文案使用“学生报名管理”。
- 每个学生一行，保留学生姓名、学校、年级、家长联系方式、绑定状态等档案信息。
- 行操作进入学生详情，不在列表中展开所有报名记录。
- 搜索仍按学生姓名、学校、家长姓名和家长手机号匹配。

### 学生详情

- 顶部展示学生档案信息。
- 下方展示“报名记录”列表，按开始日期倒序。
- 每条记录显示网点、服务项目、开始日期、结束日期和计算后的日期状态。
- 提供“新增报名记录”按钮，用于首次报名后的续费。
- 报名记录编辑和新增共用日期范围组件。
- 保存失败时保留表单内容并显示明确的日期交集错误。

## 服务端数据与校验

现有 `students` 和 `student_enrollments` 两层模型继续使用：`Student` 是学生档案，`StudentEnrollment` 是报名记录。不新增重复的学生表。

报名新增或编辑前执行：

1. 开始日期和结束日期必须存在且格式正确。
2. 结束日期不能早于开始日期。
3. 同一学生的其他报名记录中，只要满足 `existing.started_on <= new.ended_on` 且 `existing.ended_on >= new.started_on`，即拒绝保存。
4. 只检查未删除的报名记录；记录历史保留，不物理删除。

如果历史数据库存在日期为空的旧报名记录，不把它们当作可计算区间参与交集判断；新增和编辑的报名日期仍然必须完整。

## 点名筛选

点名选择网点和日期后，只返回该网点、学生状态有效且存在报名记录满足以下条件的学生：

`started_on <= selected_date <= ended_on`

因此，已过期报名不会出现在点名名单，未来报名也不会提前出现在点名名单。同一学生即使存在多条记录，也只生成一个点名卡片；日期不交集保证同一天不会命中多条报名。

## 家长端展示

- 学生档案和历史到店记录始终保留。
- 到店记录按 `attendance_date` 倒序，日期相同再按记录创建时间倒序。
- 报名日期展示从该学生的报名记录中选择一条：
  1. 优先当前生效记录；
  2. 没有当前记录时，选择开始日期最近的未来记录；
  3. 没有未来记录时，选择结束日期最近的过期记录。
- 只展示选中报名记录的开始日期和结束日期，不展示“有效期 XX 天”。
- 没有任何报名记录时，仍显示学生档案和到店记录，并提示报名信息待完善。

## 兼容与迁移

- 不删除既有学生或报名数据。
- 既有学生的第一条报名记录继续作为历史报名记录保存。
- 现有学生编辑入口调整为学生档案编辑；报名记录编辑迁移到学生详情下。
- 不同步小程序源码到腾讯云；服务端/Admin 部署只同步 `services/api/app`。

## 测试范围

- 报名日期格式、倒序日期和闭区间交集校验。
- 新增续费成功，重叠续费失败，编辑自身日期不误判。
- 点名按日期过滤当前有效报名，并对多条记录保持单个学生卡片。
- 家长端当前、未来、过期报名选择优先级。
- 家长端到店历史倒序且不因报名到期丢失。
- 后台导航、列表和详情文案。
- 服务端全量测试与小程序页面测试。
